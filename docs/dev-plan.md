# cloudfan-supabackup 开发方案（9 Phase）· v2

> 状态：v2，已根据 Codex 评审（[codex-review-1.md](reviews/codex-review-1.md)，30 项发现：P0×8 / P1×18 / P2×4）修正。P0、P1 全部采纳，P2 采纳 3 项、部分采纳 1 项，处置表见文末。
> 定位：面向独立开发者与 1–20 人小型 SaaS 团队的**纯开源、自部署** PostgreSQL 逻辑备份工具，重点适配 Supabase / Neon / Railway，备份存入用户自带的 R2 / S3 / B2。

## 0. 已锁定的决策（前提，不再重议）

| 维度 | 决策 |
|---|---|
| 产品形态 | 纯开源、自部署 Web 应用，单容器交付，不做付费 SaaS |
| 备份范围 | PostgreSQL 逻辑备份（pg_dump -Fc 主格式；Supabase 采用专用导出/恢复 profile，见 §0.5），不做物理备份 / WAL / PITR |
| 接入方式 | 连接字符串为主；三平台 API Token 辅助导入**后置到 v1.0**（beta 不做，见 §1 双轨） |
| 存储 | 用户自带 R2 / S3 / B2（BYOS）；产品只管理自己专用 namespace 下的对象 |
| 恢复 | 下载 + 恢复指南 + 生成恢复命令 + `restore.sh`（**脱离本应用运行**，不宣称零外部依赖）；不做一键恢复到生产库 |
| 差异化 | 三平台接入向导、备份覆盖范围如实声明（基于实际归档 TOC）、恢复说明包、**部署不要求 Docker socket 的嵌入式恢复验证**（注意：这是部署约束优势，**不是**安全隔离承诺，见 P6 信任边界） |
| 技术栈 | Go(chi) + React/TS/Vite + shadcn/ui + TanStack Query；SQLite(modernc, sqlc + goose)；pgx；官方 pg_dump/pg_restore；robfig/cron 仅解析时间；AWS SDK v2 transfermanager（v0.x，钉版本 + 实测）；age；OpenAPI 契约先行（oapi-codegen + openapi-typescript） |
| 镜像 | Debian slim，amd64/arm64，内置 PG 客户端 **14–18** 多版本（PG13 已于 2025-11 EOL，作为遗留兼容项不默认捆绑；PG14 于 2026-11 EOL，每次发布重核支持窗口）+ PG 服务端二进制（供验证），非 root |
| 客户端版本策略 | 优先使用与源库**同主版本**的客户端；无匹配时使用通过恢复矩阵验证的较新客户端并记录目标版本限制；manifest 记录源/dump/restore/验证目标版本与压缩算法 |
| 竞品策略 | 独立实现（不 fork Databasus）；通用修复按维护成本回馈上游；平台体验由本项目优先投入，**不主动向竞品提交三平台向导/覆盖声明/恢复包**（开源下无法也不承诺阻止他人合法复用，不使用"护城河"式排他表述）；引用竞品设计固定 commit+路径，借码保留来源与许可声明 |
| 可靠性底线 | 不静默漏备；保留锚点不被突破；重启后状态幂等收敛；工具消失备份仍可用；凭据不入日志；不伪造进度；新鲜度按**导出快照时刻**计算 |

**首版统计口径**：只记录"源库物理体积 / 已压缩 archive 字节数 / age 密文字节数"三个独立指标（标注测量口径，未测得显示未知）；导出、远端提交、恢复验证、通知结果分开统计，不混成一个"成功率"。

## 0.5 核心协议定义（v2 新增；所有 Phase 引用，来自评审最关键事项 #1）

### 协议 A：可恢复备份的提交条件链

一份备份**只有同时满足以下全部条件**才可进入"可用"状态，任一环节失败不得产生成功记录：

```
pg_dump 退出码 = 0
  ∧ 全部管道 io.Copy 成功
  ∧ age writer.Close() 成功（age 要求显式 Close 才写入末块）
  ∧ 密文文件 Sync + Close 成功
  ∧ 临时文件原子重命名提交（artifact_ready）
  ∧ [远端阶段] 上传 + 内容校验通过（协议 C）
  ∧ [远端阶段] 版本化 manifest 发布成功（远端提交标记）
  ∧ [本地] SQLite 状态更新成功
```

- 取消/超时以**进程组**终止，等待子进程退出与管道收敛；stderr 并发读取、限量保存并脱敏。
- 密文在远端提交完成前不进入可回收集合；上传重试复用同一 artifact，**绝不重新 dump**。

### 协议 B：密钥协议（两类密钥彻底分离）

| 密钥 | 用途 | 保存位置 | 丢失后果 |
|---|---|---|---|
| 应用主密钥（secret 文件） | AES-GCM 加密 SQLite 内凭据（每加密唯一 nonce；认证失败视为数据损坏，明确报错） | 实例本地，独立于数据卷说明 | 无法解密已存凭据（可重录），**不影响**备份文件可恢复性 |
| age 恢复密钥对 | 加密备份文件：实例持 recipient（公钥）加密；私钥离线保存 | 公钥指纹（key ID）记录于实例与 manifest；**私钥永不进入** manifest/恢复包/API/日志 | 历史密文永久不可读——首次生成时红字告知，UI 提供备份私钥与**试解密**流程 |

- 自动恢复验证需要实例可解密：显式挂载验证用 identity secret 并说明"实例可解密历史备份"的信任边界；未配置时验证状态为 `not_configured`，不自动降级。
- 密钥轮换 = 新备份切换 recipient；旧备份保留原 key ID 标注，**不宣称旧密文已重新加密**。

### 协议 C：SQLite ↔ 桶的远端提交协议

- `attempt`（任务尝试）与 `backup artifact`（产物）**分开建模**；每个备份有不可变 `backup_id`、目的地快照、对象键、内容大小/密文 SHA-256、可用 version ID。
- 顺序：**先落库上传意图** → 上传密文并按 §C.1 校验 → **发布版本化 manifest 作为远端提交标记** → 更新本地状态。
- 重启恢复：按持久意图与远端对象核对，幂等完成提交或续传（v1 为完整重传同一密文），不重新 dump；未提交对象隔离在待定区，宽限期后处理，**不得仅凭文件名或 running 状态清理**。
- 删除采用 `deleting → 逐对象删除（处理批量响应内逐对象错误，B2 需 versionId）→ 确认 → deleted`，可重复执行。

**C.1 内容校验（逐家明确，不笼统）**：manifest 的 SHA-256 一律指**完整密文**；每个 provider adapter 声明其小对象/分片 checksum 支持与 SDK 校验配置；无法做等价远端校验时，流式 GET 到 EOF 计算字节级 SHA-256；HEAD 大小/ETag/user metadata 均不等价于内容校验。恢复包文档注明：哈希只检错，不构成来源认证；age 不是发送者签名。

### 协议 D：保留保护协议（锚点）

- 保留按（数据库稳定 ID × 目的地 × 恢复配置域）计算；完整/结构/数据备份**分别展示**，部分备份不能替代完整备份的保护锚点。
- 删除候选 = 超期对象（已验证/未验证/失败均含），**排除保护锚点与活动引用**（上传/下载/验证任务正在使用的对象）；未验证/失败对象设显式宽限期与数量/字节预算，防无界增长。
- 锚点升级条件：新候选须远端提交 + 完整性通过 + 满足该域配置的验证等级（用户明确关闭验证的域采用完整性锚点），然后**事务替换**旧锚点。验证失败/积压**不触发**降级。
- 预算与保护冲突时：停止自动删除并告警，不突破保护规则；无锚点时禁止破坏性自动清理。
- "至少保留一份"是**本工具删除逻辑的保证**；用户侧桶生命周期规则或人工操作可破坏它——UI 与文档明确提示。

### 协议 E：manifest 自描述（脱离工具可恢复的前提）

manifest 至少包含：backup ID、格式版本、对象引用/大小/密文哈希、时间语义（**导出快照时刻**为主）、备份模式与选择/排除规则、**实际归档 TOC 对象集合**、源/dump/restore/验证目标 PG 版本、压缩算法、key ID、扩展与角色依赖、恢复 profile 及工具版本。**不含**任何密码或私钥。manifest 与恢复资料随备份发布到远端（自描述），SQLite 丢失后仍可从桶内只读发现旧备份；未确认归属与锚点前禁用旧前缀清理。

## 1. 总体节奏（双轨制，v2 修订）

**评审结论**：完整声明范围按 16–22 周 + 2–3 周风险缓冲规划；若坚持 ~14 周出 beta，必须落实右列削减。

| Phase | 完整范围工期 | beta 轨（~14 周）削减措施 |
|---|---|---|
| P1 | 1–1.5 周 | 保留骨架/认证 bootstrap/密钥协议 + 两个关键 spike |
| P2 | 2–3 周 | 保留内核、协议 A/B/E、错误分类、崩溃协议 |
| P3 | 2–3 周 | 共用 S3 adapter，R2/B2 预设后置；保留按份/按天；总量上限后置 |
| P4 | 1.5–2 周 | 保留可靠调度 + 最小失败/超期告警；子路径支持后置 |
| P5 | 3–4 周 | 三平台**连接串向导** + 恢复 profile 保留；**Token 自动导入后置** |
| P6 | 3–4 周 | 限定 PG/扩展 profile；可信来源显式启用 |
| P7 | 1–1.5 周 | Webhook + 每库死人开关 + 少量指标 |
| P8 | 2–3 周 | 安全/恢复/容量门禁保留；推广物料压缩 |

**beta 轨额外整体削减**：仅结构/仅数据两种备份模式后置到 v1.0（省去模式分离保留、验证配对复杂度）；Token 导入后置；总量上限后置；子路径后置。

里程碑：
- **M1（P2 末）**：内部原型——真实完成"通用 PG → age 加密 → 本地暂存 → 手动解密恢复"，数据一致。
- **M2（P6 末）**：**beta 功能候选（限已测试 profile）**——不称"功能完整 v1"。
- **M3（P8 末）**：公开 beta（v0.x）。
- **M4（P9）**：v1.0（完整范围 + 稳定观察窗口）。

## Phase 1 — 奠基：骨架、认证、密钥协议与两个关键 spike（1–1.5 周）

**目标**：工程底座 + 把两个最难的差异化承诺**提前证伪/证实**（评审最关键事项 #2）。

关键任务：
1. Monorepo：`backend/`、`frontend/`、`docs/`、`deploy/`、`e2e/`；`docs/adr/`。
2. 后端骨架：chi、/healthz（仅进程存活；readiness 单独回答本地状态/调度能力，**不含**桶可达性——短暂桶故障不得触发应用重启）、slog、优雅停机。
3. 前端骨架 + go:embed 单二进制；OpenAPI 契约先行，CI 校验生成物同步；服务端运行时校验独立于生成类型。
4. SQLite：modernc + goose + sqlc；**显式 PRAGMA 初始化**（所有连接：foreign_keys/busy_timeout/synchronous 策略）、短写事务；**OS advisory lock**（非锁文件存在性检测；持锁后迁移与启动，进程死亡自动释放，stale lock 不残留）；单实例本地持久卷，**明确排除 NFS/RWX 多主机**。迁移前自动生成一致 SQLite 备份（在线 backup API，非复制 .db 文件），失败拒绝提供写服务。
5. **认证从 P1 开始**（评审 P1-06）：单管理员 bootstrap 用一次性 secret 或本地 CLI（`docker exec`），**不允许公网首个访问者抢占**；密码 KDF、登录限流、安全 Cookie + CSRF；匿名仅限登录页/静态资源/最小 liveness；metrics 与详情健康检查默认受保护。
6. **Spike 1（P0-07/P0-05 前置）**：Supabase 真实项目 → pg_dump -Fc → **新建 Supabase 项目恢复**实测，验证官方角色/结构/数据分离流程的可行 profile（产出 ADR-003）；若必须改变产物格式，先 ADR 决策。
7. **Spike 2**：发布形态容器内非 root `initdb` 临时 PG 可行性（文件/进程隔离实测、双架构打包、资源占用），产出信任边界 ADR-004。
8. 许可证定版（ADR-000，建议 AGPL-3.0；ADR 写明社区贡献/托管使用目标，**不承诺 AGPL 能阻止合规托管**）；ADR-001 技术选型；ADR-002 不 fork Databasus。

DoD：
- compose 一键起开发环境；CI 全绿含契约同步检查；
- 认证 bootstrap 抢占测试（公网首访不能成为管理员）；
- advisory lock 实测拦截双实例；迁移前备份与失败拒写实测；
- 两个 spike 有书面结论与 ADR。

## Phase 2 — 备份执行内核：协议 A/B/E 落地（2–3 周）

**目标**：备份内核在本地暂存上完整可靠，密钥协议闭环，错误分类就位。对应 M1。

关键任务：
1. **协议 B 落地**：age recipient 首次配置（含 key ID 指纹、私钥离线保存引导、试解密流程）；凭据 AES-GCM（唯一 nonce、认证失败显式报错、密钥文件权限）；日志/错误/API/生成命令四出口全链路脱敏。
2. 连接测试（pgx）：可达性、版本（按 §0 客户端版本策略选客户端）、权限、TLS（pgx 与 libpq **统一** host/user/db/TLS/CA 语义；远程默认推荐 verify-full，未验证证书与明文连接需显式配置并持续显示状态）；URI 解析为受支持字段，**限制** passfile/service/sslkey/options 等自由参数。
3. **协议 A 落地**：pg_dump 执行链（os/exec 直传参数、argv 无密码、PGPASSFILE 0600/目录 0700/冒号反斜杠转义/全分支清理、启动时清理继承的 PG* 环境变量）；原子提交与故障路径。
4. 任务状态机：`pending → running → succeeded/failed/canceled/interrupted` + `error_class`（网络/认证/权限/客户端版本/磁盘/存储上传/验证失败七类 + `retryable` 标志 + 错误码，v2 从 P2 开始而非 P8）；启动将 running 标记 interrupted。
5. pgx 连接测试与 pg_dump 连接一致性（同参数同 TLS 语义）。
6. 依赖采集（为 P6 profile 与协议 E）：所需扩展及版本、角色引用、编码/locale、owner/ACL、large objects、FDW 外部表（声明为非默认覆盖）。
7. 暂存目录：独立配额、预检（按解压后估算而非密文大小）、写满清理、孤儿回收。
8. manifest v1（协议 E）；本地磁盘目的地。
9. 测试：Testcontainers 真实 PG；故障注入（见 §跨 Phase 矩阵）；`-race`（仅覆盖 Go 内存竞态，不替代一致性测试）。

DoD：
- "先输出数据再非零退出"的 dump、Close/Sync 失败、消费者提前失败、取消时子进程存活——**均不能进入成功状态**，无死锁/泄漏/误删待重传文件；
- age 流式实现内存 RSS 有上限断言；
- **M1**：删掉应用容器与 SQLite，仅凭暂存密文、离线私钥、age/PG 工具在全新 PG 恢复成功，数据核对一致；
- 植入 secret canary（含特殊字符口令）扫描日志/错误/argv（/proc 实查）/生成命令。

## Phase 3 — 对象存储、远端提交与保留锚点（2–3 周）

**目标**：协议 C/D 落地，三存储真实可用，删除绝不误删。

关键任务：
1. S3 兼容目的地（transfermanager 钉版本）：上传/下载/删除/预签名 URL；**每个 provider adapter 声明**分片阈值、checksum 支持、版本化行为、删除语义（B2 versionId）、分页上限，逐家实测（不只 MinIO）。
2. 存储配置向导：专用诊断 namespace 下写→读→清理（与正式备份 namespace 分离，不干扰保留/对账）；周期性写读删探测默认关闭（成本与对象回收说明）。
3. **协议 C 落地**：意图落库 → 上传校验（C.1 逐家协议）→ 版本化 manifest 发布 → 本地状态；上传重试复用密文；multipart 遗留 abort 与分片回收指导。
4. **协议 D 落地（beta 简化形）**：按份数/按天数保留；保护锚点（beta 用完整性锚点，P6 升级验证锚点）；失败对象宽限期与预算；deleting 状态机；只管理自己 namespace；桶生命周期冲突提示。
5. **桶对账升级**：分页列表 vs manifest 目录（SQLite 丢失后的只读发现路径）；缺失/多余/未提交分别呈现；确认归属前禁用清理。
6. 自身状态备份（P0-08 前移）：一致的 SQLite 在线备份流程 + 主密钥/私钥独立保管说明文档。

DoD：
- **在每个外部副作用前后强制崩溃**（上传完成→落库前、manifest 发布前后、删除确认前后），重启后不重复导出、不把未提交备份算作可恢复、不误删待重传密文；
- 进程死于 multipart 中、>1000 对象分页、B2 历史版本、批量删除部分失败、锁定对象拒删、权限不足——全部有确定行为；
- 错误 checksum、metadata 正确但内容错误、同大小替换、缺 checksum 响应——完整性校验全部拦截（真实三桶用例）；
- 保留注入故障下锚点不被突破（验证连续失败 30 次场景此时以"未验证+宽限预算"处理，不无界增长）。

## Phase 4 — 调度、并发治理与最小告警（1.5–2 周）

**目标**：从手动到"部署后持续正确工作"，排队与新鲜度语义明确。

关键任务：
1. 持久化调度：入队与 next_due 更新**同一 SQLite 事务**；唯一键 `(database_id, schedule_revision, scheduled_at_utc)`；重试关联原任务，手动任务独立幂等键；pending 有界、同库过期合并、公平轮转；上传长重试等待释放执行槽；任务保存**配置快照**，改 cron/暂停/删除时显式处理 pending 与活动引用；cron 存 IANA 时区并定义 DST 语义；任务时限用单调时间、计划时刻用 UTC；错过补跑最近一次并标注。
2. 每库"最大可接受备份年龄"配置；新鲜度按**导出快照时刻**计算（不是任务结束/上传完成时刻）；记录计划/开始/快照/上传提交/验证完成各时刻。
3. **最小失败/超期告警**（P7 完善前先可用）：失败与超期的 Webhook + 日志事件。
4. 生产库影响控制：低峰建议、执行超时、锁等待提示文档化。
5. 运维：advisory lock 已在 P1；/metrics（默认受保护；label 不含 task/backup/table ID 与自由错误文本，明细在 SQLite）。

DoD：
- 入队事务前后崩溃、跳过多周期、时钟前后跳、DST、暂停/改计划、长上传重试与立即备份并发——唯一性与有界队列全部断言；
- 一个超长任务 + 三个竞争库 + 断网跨多周期：超期状态正确、能力不足可见而非静默积压；
- 改配置后旧任务用快照配置完成，不混乱。

## Phase 5 — 三平台向导与恢复包（3–4 周；beta 轨无 Token 导入）

**目标**：差异化核心——接入友好 + 覆盖诚实 + 恢复可用。

关键任务：
1. **平台适配（连接串兜底；识别用官方 endpoint 特征 + 连接行为，端口仅提示，保留用户确认）**：
   - Supabase：Supavisor 池化识别（**不以端口号臆断**；IPv4-only 环境引导官方 session pooler，不臆造 host）；覆盖范围面板基于**实际归档 TOC**：包含/排除/平台外部资源三段式；Supabase 专用导出/恢复 profile（P1 Spike 1 结论落地：角色/结构/数据处理、Auth/Storage 元数据与 Vault 的范围如实声明——beta 若仅支持应用 schema，明写"应用 schema 逻辑备份"，不暗示全量平台备份）；不重置密码。
   - Neon：直接连接引导（池化检测）、分支上下文命名、**compute 冷启动的独立连接超时**（区分暂时启动与认证失败）。
   - Railway：从部署位置实测可达性；私网地址可达时**合法放行**，不可达才引导 TCP proxy；错误提示可行动。
   - 通用 PG：P2 检查整合入向导。
   - API Token 导入（v1.0）：先以真实只读 Token 记录各平台 API 可返回字段/权限范围/分页/限流/撤销行为；**Supabase PAT 不能取得现有数据库密码**——缺凭据时明确要求用户粘贴，不臆造；mock fixture 从真实 API 脱敏样本生成。
2. **恢复说明包**：manifest + 校验（注明哈希检错非签名）+ 平台感知恢复指南（Supabase 按 profile，不套通用模板）+ 按目标类型生成命令 + `restore.sh`：固定模板 + 安全参数传递（**不拼用户字段为 shell**）；启动前自检（工具/版本存在、密文哈希核对、目标为新建空库、profile 依赖）；受限 PGPASSFILE；串行流恢复 `--exit-on-error` + age 与 pg_restore 双端退出码检查；默认无 --clean/--create；失败非零退出并说明"目标可能已部分写入"；并行恢复需先解密到 0600 临时文件并提示明文落盘边界；明确支持 Linux/macOS 与 shell 要求。
3. 下载通道：短期预签名 URL 直连用户桶（bearer secret 脱敏；不代理任意 URL 下载）；URL 当作秘密。
4. SSRF 边界（P1-07）：平台 API 固定官方 origin、不接受自定义 base URL、不向跨 origin 重定向转发 Token；Webhook/死人开关/自定义 endpoint 仅允许规定 scheme、超时与响应体上限、默认拒绝 metadata/link-local（内网 PG/MinIO 属正常功能，经管理员显式配置放行；解析与重定向均复核地址）。
5. 覆盖范围用语统一（P1-10）：产品用语为"**所选范围的结构+数据逻辑备份**"；高级选项修正为"schema 包含 `-n` / 排除 `-N`"；跨 schema 依赖预检、缺依赖列入恢复前置；**禁止静默 `--enable-row-security`** 绕过权限错误，失败明确报告覆盖不足。

DoD：
- 三向导走通"粘贴连接串 → 正确选中对象 → 首次备份成功"；
- **真实发布门禁**：三平台各一次"备份 → 从桶下载 → 依恢复包在**新建目标**手动恢复"成功（自动验证是额外门禁，**不作为替代**），提交演练记录（artifact ID/profile/工具版本/fixture 断言）；
- 池化/私网/权限不足/Token 受限四类误配置给出可行动提示；restore.sh 在无本工具的全新主机通过错私钥/缺工具/非空目标/SQL 错误用例。

## Phase 6 — 嵌入式恢复验证（3–4 周，限 profile）

**目标**：恢复验证真实可信，不过度承诺。

关键任务：
1. **验证 profile**：为已测试的（PG 版本 × 扩展组合）维护 profile（固定目标版本、角色初始化、恢复选项）；P2 采集的依赖决定 profile 支持；不支持的依赖 → `unsupported`，资源超限 → `skipped`，SQL/解密失败 → `failed`，三者均非通过；通过状态显示"**在 profile X 上按选项 Y 恢复成功**"，与"平台完整恢复演练"分开呈现。
2. **信任边界（P0-05，依 P1 Spike 2 ADR）**：验证仅监听独占目录 Unix socket（禁 TCP）；v1 自动验证**仅支持管理员信任的来源**，不承诺不可信 dump 沙箱；发布文档与 UI 明示该边界并要求显式启用；CI 验证容器不注入平台/桶真实凭据；需要不可信来源时用独立受限验证环境（无共享 secrets/数据卷），**不用 nice 冒充隔离**。
3. 资源治理（P1-04）：验证并发固定 1、有界队列，积压合并或显式 skipped；磁盘按**解压后**数据+索引+WAL 峰值预留（密文小≠恢复小）；wall-time 超时；备份优先，验证预算不足时延后；退出与启动回收残留 PG 进程/socket/目录。
4. 验证判据（P1-03）：最低判据 = 远端完整读取/解密成功（可与完整性校验 C.1 合并，避免二次下载）+ `pg_restore --exit-on-error` 零错误 + 预期 TOC/对象集合恢复；估算行数与体积仅作诊断输出（明确标注估算与未 ANALYZE 局限）；CI 用静态 fixture 已知精确数据断言；并发写入/过期统计/空表/分区/索引重建不产生假成功或假失败。
5. **协议 D 升级**：验证锚点生效（新锚点须验证等级达标后事务替换）；验证失败/积压不降级；beta 无仅结构/仅数据模式，v1.0 增加时：仅结构只验结构、仅数据须绑定 schema 基线否则不提供独立恢复验证。
6. Supabase 验证 profile：裸 PG 验证通过**不等于**可恢复到新 Supabase 项目——平台演练单独记录（P5 门禁），UI 分开呈现。

DoD：
- CI 全自动：标准 fixture 备份→验证→销毁闭环（含精确数据断言）；
- 损坏注入分类正确：传输截断 / 合法 age 封装的无效 dump / 缺角色扩展的 SQL 错误 / 声明对象缺失——各自得到确定结果，**不靠忽略 SQL 错误变绿**；
- 高压缩比 fixture、验证 OOM、磁盘写满、超时、重启——主备份链按明确策略工作，残留全回收；
- 全程无 Docker socket、无特权、非 root；隔离边界有测试证据或明确"可信来源"限制。

## Phase 7 — 通知、死人开关与可观测（1–1.5 周）

关键任务：
1. **通知 outbox**（P1-12）：状态提交与 outbox 同事务；异步发送、有界重试退避、event ID 去重；发送失败不回滚备份、状态可查、有测试按钮。
2. **死人开关绑定真实新鲜度**：每库独立配置外部周期与 grace（覆盖排队+执行耗时）；成功 ping 的等级 = 至少远端提交 + 完整性通过；**同时校验快照年龄**——旧密文晚上传成功不得消除超期；start/fail/success 按协议区分；健康检查成功不发备份成功 ping。
3. 周期健康检查（P2-04）：低频 + jitter + 超时；连通性探测默认优先使用最近实际备份结果；完整写读删探测仅初始化与用户主动诊断；Neon 不因探测唤醒 compute（或明示代价）。
4. 首页回答"哪些库没有足够新的成功备份"：最近任务与最近成功备份两列；失败重试中不显示为受保护；超期/未验证/从未成功分列；按快照时刻算年龄，验证新鲜度另列。
5. /metrics：任务数、远端提交成功率、验证状态分布、上次成功时间戳、暂存占用（无高基数 label）。

DoD：
- 提交后发送前 crash 不漏通知；Webhook 429/超时/重放去重正确；
- 关机场景死人开关按时触发（外部服务实测 + 文档）；
- 四种首页状态显示正确；验证失败但远端有效时两种状态不混淆。

## Phase 8 — 打磨、门禁与公测发布（2–3 周）

关键任务：
1. 统计落库与表格展示（三体积指标 + 分段成功率，见 §0）；失败诊断七类的排查文案补全（AI 解释仅内部模块边界预留，**不进公开契约**）。
2. **升级门禁（P0-08）**：上一公开版本 → 新版本前向迁移真实测试；迁移失败恢复演练；SQLite/WAL 丢失、应用主密钥丢失、仅桶+私钥幸存三场景有确定行为与文档。
3. 安全审计：govulncheck、trivy、gitleaks、四出口 secret canary 复查。
4. 容量与性能（P1-13）：固定测试机条件 + 至少一个低压缩比 fixture，报告 dump/upload/verify 分段耗时、峰值 RSS/磁盘、支持的总负载边界（所有库总耗时 vs 调度周期的稳定条件），文档写明 RPO 语义（受间隔/排队/执行/故障影响，不承诺 PITR）。
5. 发布材料与检查清单：README（差异定位用**可测试差异**表述，不用 stars 排名）、部署文档、恢复演练文档、CHANGELOG。
6. 公测发布（v0.x）：HN / Reddit / V2EX / Supabase 社区；issue 分类（可靠性 > 平台适配 > 体验）。

**统一发布门禁（P1-15，beta 与 v1 共用）**：
- 三平台各一次真实"备份 → 从桶下载 → 依恢复包在新目标手动恢复"（自动验证为额外门禁，不可替代）；提交脱敏演练记录；
- CI 可判定每项门禁通过/失败；新增未测试平台或未解决 P0 自动阻止发布；
- v1.0 额外要求：已知 P0 为 0、恢复相关 P1 已关闭或公开缩减支持范围、稳定观察窗口内无未解释的成功假象/误删。

## Phase 9 — v1.0 稳定化与后续迭代（首个迭代约 3 周 + 持续）

关键任务：
1. 稳定化：公测 issue（可靠性优先）；长期运行观测（误删/成功假象为零是硬指标）。
2. **v1.0 范围补齐**：Token 自动导入（P5 预研落地）、仅结构/仅数据备份模式（含协议 D 模式分离与验证配对）、子路径部署、总量上限。
3. 恢复演练文档化：季度演练指南 + 工具内记录演练结果。
4. 密钥轮换 UX 完善（协议 B）。
5. 上游回馈：通用修复（版本校验、连接检测类）按维护成本整理 PR。
6. v1.0 发布：**稳定承诺限定**于 manifest/恢复包格式版本兼容、CLI 恢复入口、公开自动化 API；内部 UI API 可随版本演进；旧 manifest 能被新恢复脚本识别，未知版本明确失败。
7. 第二层能力（schema diff / 体积异常 / 恢复风险检查）**另立后续迭代**，不进 v1.0。

DoD：见 Phase 8 统一门禁 + 升级路径实测 + 迁移文档齐备。

## 跨 Phase 工作流

**故障注入矩阵（P1-14 升级）**——在**外部副作用边界**设可定位注入点：dump 退出 / age Close / 文件 Sync / multipart 完成 / manifest 发布 / SQLite 提交 / 通知 outbox / 删除前后；覆盖：源端并发写入、控制状态盘 ENOSPC、SQLITE_BUSY、OOM/kill、取消、密钥错误、删除与验证并发。PG fixture 覆盖 bytea/大字段、sequence、分区、FK、索引、视图、RLS、角色、已支持扩展（pgvector 等）；静态数据精确核对；DoD 记录 fixture ID、seed、工具/profile 版本。特权注入在 CI 夹具做；发布容器另做非 root/无 socket 黑盒测试。

**测试分层**：Go 单测 + fake clock 测调度；真实 PG（Testcontainers）集成；真实三桶（发布门禁）+ MinIO（日常）；Vitest；Playwright UI 状态；`-race` 仅作内存竞态补充。

**Databasus 参考阅读**（固定 commit + 路径引用，借码保留来源/许可/改动声明）：P3 前 GFS 与验证门控设计；P5 前平台连接与错误分类；P6 前恢复验证实现（对照无 socket 方案找坑）；随时借工程实践（Trivy/semgrep/gitleaks、备份后真恢复 e2e）。

## 明确不做（beta 与 v1.0）

MySQL/MariaDB/MongoDB；物理备份与 WAL/PITR；Supabase Storage 文件备份；平台完整克隆与跨云迁移；一键恢复到生产库；自动数据库优化；图表化仪表盘；多用户/工作区/RBAC；OAuth；AI 默认开启；Redis/消息队列/微服务；K8s 为部署前提；不可信 dump 的沙箱验证（v1 明确不支持，见 P6 信任边界）；NFS/网络文件系统上的多实例部署。

## 依赖与外部前提

R2/S3/B2 测试桶与少量预算；Supabase/Neon/Railway 各一个真实测试项目与 API Token；healthchecks.io 或等价服务；固定规格的容量测试机。
