# cloudfan-supabackup 开发方案（9 Phase）

> 状态：待评审 → 已根据 Codex review 修正（见文末评审记录）
> 定位：面向独立开发者与 1–20 人小型 SaaS 团队的**纯开源、自部署** PostgreSQL 逻辑备份工具，重点适配 Supabase / Neon / Railway，备份存入用户自带的 R2 / S3 / B2。

## 0. 已锁定的决策（本方案的前提，不再重议）

| 维度 | 决策 |
|---|---|
| 产品形态 | 纯开源、自部署 Web 应用，单容器交付，不做付费 SaaS |
| 备份范围 | PostgreSQL 逻辑备份（pg_dump -Fc），不做物理备份 / WAL / PITR |
| 接入方式 | 连接字符串为主 + 三平台 API Token 辅助导入（发现项目、补上下文），OAuth 不做 |
| 存储 | 用户自带 R2 / S3 / B2（BYOS），产品自身不存备份数据 |
| 恢复 | 下载 + 恢复指南 + 生成恢复命令 + 自包含 restore.sh；不做一键恢复到生产库 |
| 差异化 | 三平台接入向导、备份覆盖范围诚实声明、恢复说明包、**无 Docker socket 的嵌入式恢复验证** |
| 技术栈 | Go(chi) + React/TS/Vite + shadcn/ui + TanStack Query；SQLite(modernc, sqlc + goose)；pgx；官方 pg_dump/pg_restore；robfig/cron 仅算时间；AWS SDK v2（新 transfermanager）；age 加密；OpenAPI 契约先行（oapi-codegen + openapi-typescript） |
| 镜像 | Debian slim，amd64/arm64，内置 PG 客户端 13–18 多版本 + PG 服务端二进制（供验证），非 root 运行 |
| 竞品策略 | 不 fork Databasus（Apache-2.0，30 万行级 monorepo，架构反向）；将其作为参考实现读 ADR/openspec，小模块按 Apache 规矩借用，通用改进回馈上游；不向竞品 PR 三平台向导/覆盖声明/恢复包（护城河不上交） |
| 可靠性底线 | 不静默漏备；只保护"最新通过验证的备份"；重启后状态不混乱；工具消失备份仍可用；凭据不入日志；不伪造进度 |
| 首版统计 | 只记录与表格展示，不做图表与趋势分析（第二层能力） |

## 1. 总体节奏

```
P1 奠基 ─ P2 备份内核 ─ P3 对象存储与保留 ─ P4 调度与安全
      └────────────► 主干优先：先让"接入→加密备份→上传→下载恢复"跑通，再谈平台向导
P5 三平台向导+恢复包（差异化核心）─ P6 嵌入式恢复验证（差异化武器）
P7 通知与可观测 ─ P8 打磨与公测发布 ─ P9 v1.0 稳定化与第二层能力
```

- **里程碑 M1（P2 末）**：内部原型——真实完成一次"通用 PG → 加密 → 本地暂存 → 手动恢复"。
- **里程碑 M2（P6 末）**：功能完整的 v1 代码——三平台 + 三存储 + 验证 + 恢复包全部可用。
- **里程碑 M3（P8 末）**：公开 beta（v0.x），对外发布。
- **里程碑 M4（P9 中）**：v1.0。

时间假设：1 名主力开发 + AI 辅助，全职投入。P1–P8 合计约 14 周（各 Phase 给出区间，见各节）。若兼职投入按比例拉长。

## Phase 1 — 奠基：仓库骨架、契约先行、CI、许可证（约 1 周）

**目标**：建立可持续演进的工程底座，走通"前后端 + 容器 + CI"的最小主干。

关键任务：
1. Monorepo 结构：`backend/`、`frontend/`、`docs/`、`deploy/`、`e2e/`；`docs/adr/` 建立 ADR 习惯。
2. 后端骨架：Go module、chi 路由、/healthz、结构化日志（slog）、优雅停机。
3. 前端骨架：Vite + React + TS + shadcn/ui + TanStack Query；`go:embed` 嵌入静态资源，单二进制服务页面与 API。
4. **OpenAPI 契约先行**：`api/openapi.yaml` 为唯一事实源；CI 校验 oapi-codegen / openapi-typescript 生成物与契约同步；服务端运行时参数校验不依赖生成类型。
5. SQLite 接入：modernc.org/sqlite + goose 迁移 + sqlc 生成；WAL 模式；`data/` 持久化目录约定。
6. Docker 开发环境：compose 起 PG 测试库 + MinIO（S3 兼容模拟）+ 应用；多阶段构建出正式镜像骨架。
7. CI：build + lint（golangci-lint / eslint）+ 单测 + 前端构建；主干保护。
8. **许可证定版**（ADR-000）：默认建议 **AGPL-3.0**（防云厂商复包装，与定位一致）；备选 MIT。落 LICENSE / NOTICE / README 骨架（README 写清与 Databasus / pgBackWeb 的差异定位）。
9. ADR-001 技术选型记录；ADR-002 记录"不 fork Databasus"的决策与理由。

完成标准（DoD）：
- `docker compose up` 一条命令起完整开发环境；
- CI 全绿，含"契约与生成物不同步即失败"的检查；
- 镜像内含非 root 运行用户；/healthz 可访问。

风险与对策：sqlc + modernc 组合的边缘问题 → P1 内先做一个含事务与并发的冒烟 DAO 测试，早暴露。

## Phase 2 — 备份执行内核：任务状态机 + pg_dump + age 加密（约 2 周）

**目标**：不碰对象存储，先让备份执行内核在本地暂存上完整可靠。对应里程碑 M1。

关键任务：
1. **凭据加密存储**：AES-GCM（应用主密钥文件，环境变量指路径）；连接串、存储凭据、平台 Token 落库前加密；日志与错误全链路脱敏（连接串掩码）。
2. 数据库实体与连接测试（pgx）：可达性、服务器版本、权限（pg_dump 所需）、TLS；**客户端版本矩阵**：镜像装 PG 13–18 客户端，执行前匹配"客户端主版本 ≥ 服务器主版本"，不满足则明确报错。
3. **任务状态机**（SQLite 表）：`scheduled_at / attempt / started_at / heartbeat_at / finished_at / status / error_class`；状态：pending → running → succeeded / failed / canceled / interrupted；API"立即备份"只创建任务立即返回任务 ID。
4. Worker：单实例内全局并发 1（v1 固定），同一数据库不重叠（DB 级互斥）；心跳更新；启动时将 `running` 标记为 `interrupted` 而非成功/重跑。
5. **执行链路**：预检（连接、权限、暂存目录磁盘余量 ≥ 预估体积倍数）→ pg_dump -Fc（os/exec 直传参数 + 权限受限的临时 PGPASSFILE，不拼 shell）→ 流式 age 加密写暂存密文 → 记录 SHA-256 与大小 →（本 Phase）落"本地磁盘"目的地 → 清理暂存。
6. 暂存目录：独立配额、写满即失败并清理、中断文件回收（启动时孤儿清理）。
7. 备份清单（manifest）v1：来源、版本、时间、模式、覆盖范围、校验和——与密文分开存放。
8. 测试：Testcontainers 起真实 PG 做单测/集成；**失败注入**：导出中断（kill）、磁盘写满（tmpfs 限额）、重启恢复；竞态检测 `go test -race`。

DoD：
- 对 Testcontainers PG 完整跑通"手动触发 → 加密暂存 → 清单落库"；
- 中断/写满/重启三类故障注入全部状态正确、暂存无孤儿；
- **真实完成一次手动恢复**：下载暂存密文 → age 解密 → pg_restore 到全新 PG → 数据与结构核对一致（M1 达成）；
- 日志中搜不到任何明文密码/连接串。

风险：age 流式加密的内存边界 → 用 `io.Pipe` 流式实现并在大对象测试中观测内存 RSS 上限。

## Phase 3 — 对象存储与保留策略（约 2 周）

**目标**：R2 / S3 / B2 真实可用，保留策略绝不误删。

关键任务：
1. S3 兼容目的地（AWS SDK v2 新 transfermanager）：上传、下载、删除、预签名 URL；R2 / B2 作为预设 + **逐家兼容性测试**（分片阈值、校验和、删除行为、错误码），不只测 MinIO。
2. 存储测试向导：专用前缀下写入→读回→清理小文件，通过才算配置成功。
3. 上传重试：**暂存密文重传，绝不重新 dump 生产库**；指数退避；上传后按约定校验（远端回读校验或等价机制，不只对本地哈希）。
4. 备份生命周期状态：导出完成 → 上传完成 → 完整性已校验 →（P6 增加）恢复已验证；每态独立可查。
5. **保留策略**：按份数 / 按天数；三种模式（完整/仅结构/仅数据）**分开计数**；只清理本工具专用前缀下对象；"保护最新一份完整备份"（P6 后升级为"最新通过验证的备份"）；清理失败与备份失败分开记录；可选总量上限（保护用户账单）。
6. **桶对账**：定期列桶内对象 vs 本地清单，缺失/多余分别报告，UI 如实显示"清单与实际不一致"。
7. 失败注入：上传中断网、上传中重启、对账发现人为删除的对象。

DoD：
- 三个真实桶（R2/S3/B2）各跑通完整生命周期 + 故障注入；
- 保留清理在任何注入故障下都不删除"最新完整备份"；
- 对账能发现并正确呈现人为删除。

## Phase 4 — 调度、多数据库与安全基线（约 1.5 周）

**目标**：从"手动触发"进化为"部署后持续自动工作"，并封住安全与运维基线。

关键任务：
1. 持久化调度：robfig/cron 仅解析/计算下次时间，执行计划落 SQLite；错过的调度**只补跑最近一次**（catch-up latest），UI 标注"本次为补跑"；时区显式存储与展示。
2. 任务管理 UI：列表、详情、暂停/恢复数据库、取消任务、失败重试；日志按次落库可查。
3. 备份模式：完整 / 仅结构 / 仅数据（保留计数分离已在 P3 处理）；高级选项（schema 排除 `-n/-N` 等）默认折叠。
4. 认证与访问：单管理员 + 服务端 Session（安全 Cookie、CSRF）；关闭公开注册；`docker exec` CLI 重置密码；反向代理子路径部署支持。
5. 运维防呆：实例锁文件（第二个副本挂同一卷拒绝启动）；/metrics（Prometheus，可选开关）；/healthz 分级（存活 / 调度器心跳）。
6. 生产库影响控制（文档 + 实现）：低峰调度建议、pg_dump 执行超时上限、对"长事务/锁等待"的提示文档化（备份负载影响写进 README 与数据库详情页）。

DoD：
- 多数据库（≥3）定时备份在重启、时钟变更场景下调度正确、不重叠、不重复补跑；
- 双实例误部署被锁文件拦截；
- 未认证访问 API/UI 全部 401。

## Phase 5 — 三平台向导与恢复包：差异化核心（约 2.5 周）

**目标**：把"对 Supabase / Neon / Railway 更友好、对覆盖范围更诚实、对恢复更有用"做实。

关键任务：
1. **平台适配层**（连接字符串永远兜底）：
   - Supabase：API Token 导入项目列表与连接信息；**Supavisor 池化检测**（事务模式 6543 → 引导改直连/会话模式）；覆盖范围面板：包含的 schema/对象、排除项、明确"Storage 文件 / Edge Functions / 平台配置不在范围"；Vault/额外密钥恢复前置提示；绝不自动重置数据库密码。
   - Neon：API 列项目/分支/数据库；池化连接检测 → 引导直接连接；展示带分支上下文的名称（`项目 / 分支 / 库名`）。
   - Railway：API 列项目/服务；私网地址检测 → 可行动的错误提示（而非裸 timeout）；要求可达的 TCP 代理连接。
   - 通用 PostgreSQL：版本/权限/TLS 检查（P2 已有，此处整合入向导）。
2. **恢复说明包（Recovery Kit）**：manifest + 校验信息 + 平台感知的恢复指南（Supabase 按 Supabase 官方恢复注意事项生成，不套通用模板）+ 按目标类型生成恢复命令 + **自包含 `restore.sh`**（age 解密 + pg_restore + 基本校验，不依赖本工具运行）；默认引导恢复到新建测试库，不生成覆盖生产库的命令。
3. 数据库详情页"备份覆盖范围"区块：包含什么/排除了什么/不在范围什么，三段式如实展示。
4. 下载通道：**预签名 URL 直连用户桶**（不流经应用内存）+ 本地 age CLI 解密说明。
5. e2e（Playwright）：三平台向导用 mock API 走通；真实平台账号做发布前手测清单。

DoD：
- 三个向导各自走通"粘贴 Token/连接串 → 选中正确对象 → 首次备份成功"；
- 每平台至少一次**真实**备份→下载→按恢复包手动恢复成功（发布门禁的一部分）；
- 池化/私网/权限不足三类误配置均给出可行动提示（不允许裸报错）。

## Phase 6 — 嵌入式恢复验证：差异化武器（约 2 周）

**目标**：实现"恢复已验证"状态，且不挂 Docker socket、不要求特权。

关键任务：
1. **嵌入式验证器**：容器内 `initdb` 临时实例（非 root、临时目录、随机本地端口、CPU nice + 超时）→ pg_restore 密文解密后恢复 → 比对表数量、逐表行数估算、数据库大小 → 比对结果落库 → 销毁实例与临时目录。
2. 资源治理：按数据库开关（默认开启但受体积阈值限制，超阈值默认关并提示）；验证失败不删除备份，只标记状态并告警；验证不阻塞备份主链路（异步任务）。
3. **验证门控保留**：仅"通过恢复验证"的备份计入保留名额（与"保护最新完整备份"合并为"保护最新可用备份"）；无验证时回退为保护最新完整性校验通过的备份。
4. 状态链完整呈现：导出完成 / 上传完成 / 完整性已校验 / 恢复已验证 四态独立展示，未验证如实显示"尚未进行恢复验证"。
5. 测试：CI 中对真实 PG 跑"备份→验证→销毁"全链路；注入坏备份（截断密文）验证能被发现。

DoD：
- 标准库备份在 CI 全自动通过恢复验证（含行数比对）；
- 截断/损坏备份被验证器识别并正确标记；
- 全程无 Docker socket、无特权、非 root；
- 保留清理遵守验证门控。

参考实现：Databasus `adr/` 与恢复验证模块（Apache-2.0，学设计不抄核心码，边界：独立小函数可带声明借用）。

## Phase 7 — 通知、死人开关与可观测性（约 1 周）

**目标**：补上"工具本身死了也要有人知道"的洞，让首页回答唯一重要的问题。

关键任务：
1. 通用 Webhook 通知：备份成功/失败、验证失败、保留异常、对账不一致、健康检查失败等事件，可配订阅。
2. **死人开关（dead-man's switch）**：每库成功备份后 ping 外部 URL（兼容 healthchecks.io 协议）；静默超时由外部服务告警——覆盖"实例宕机/被删/断电"场景。
3. 周期健康检查：数据库可达性 + 存储目的地可用性（复用 P2/P3 的测试逻辑，定时化）。
4. 首页仪表盘回答核心问题："**哪些数据库目前没有足够新的成功备份？**"——同时展示最近任务与最近成功备份两列，失败重试中不得显示为"受保护"；需要关注列（超期/未验证/从未成功）。
5. /metrics 暴露：任务数、成功率、上次成功时间戳、验证状态分布、暂存占用。
6. 通知脱敏复用 P2 的脱敏层。

DoD：
- 关机场景下外部死人开关服务按时触发告警（手测 + 文档）；
- 首页在"从未成功 / 失败重试中 / 超期未备 / 未验证"四种状态下显示正确的关注提示；
- Webhook 事件含足够排障信息且无凭据。

## Phase 8 — 统计记录、诊断分类、打磨与公测发布（约 2 周）

**目标**：发布对外 beta（v0.x），README 能让目标用户 3 分钟内明白为什么用它而不是 Databasus/pgBackWeb。

关键任务：
1. 统计记录（只记录 + 表格展示）：数据库大小、表数量、dump 大小、压缩后大小、耗时、成功率历史——**三个体积指标分开记录**（库体积/导出体积/密文体积）；行数用统计信息并明确标注"估算"。
2. 失败诊断分类：网络/认证/权限/客户端版本/磁盘/存储上传/验证失败 七类的结构化错误码 + 每类的排查建议（AI 解释位留接口，默认关闭，不接模型功能完整）。
3. 打磨：空状态、错误态、加载态全过一遍；时区显示统一；大备份下载体验（预签名 + 浏览器直下）。
4. 安全审计：govulncheck、镜像 trivy 扫描、gitleaks、脱敏专项复查（日志/错误/Webhook/生成的命令四出口）。
5. 性能与容量：≥5GB 库的端到端备份测试（观测内存 RSS、暂存占用、耗时）；文档给出资源建议。
6. 发布材料：README（差异定位 + GIF 演示）、部署文档（compose / 反代 / 子路径）、恢复演练文档、CHANGELOG；发布检查清单（三平台真实备份+恢复验证各过一遍）。
7. 公测发布：打 v0.x tag，提交 HN / Reddit / V2EX / Supabase 社区；收集 issue 分类（可靠性 > 平台适配 > 体验）。

DoD：
- 发布检查清单全绿（含三平台真实恢复演练）；
- 安全扫描无高危未处理项；
- 首页 + README + 部署文档三件套齐备。

## Phase 9 — v1.0 稳定化与第二层能力起步（持续，首个迭代约 3 周）

**目标**：从 beta 到 v1.0，并按数据开启第二层（洞察）能力。

关键任务：
1. 稳定化：处理公测 issue（可靠性优先）；升级与数据迁移路径测试（goose 前向迁移 + 备份自身数据指导）；崩溃与超时长期观测。
2. **恢复演练文档化**：官方"季度恢复演练"指南（用本工具的恢复包在全新环境完整演练一次），并鼓励用户把演练结果记录到工具内。
3. 第二层能力第一迭代（按公测反馈排序，预计只做 1–2 项）：备份体积异常检测（突大/突小说明）/ Schema Diff（两次结构快照对比，新增-删除-修改对象）/ 恢复风险检查（目标环境缺扩展/角色预检）。
4. 密钥轮换路径：恢复密钥轮换（新备份用新钥，历史备份标注所属密钥）；丢失恢复私钥的红字警示与 UX。
5. **上游回馈**：把通用增强（如 pg_dump 版本校验、池化连接检测类改进）整理 PR 给 Databasus / pgBackWeb——只回零件，不回三平台向导/覆盖声明/恢复包。
6. 国际化预留（如社区有需求）、Rclone 桥接存储（低成本扩展 GDrive/Dropbox/SFTP）评估。
7. v1.0 发布：API 冻结承诺、语义化版本、升级文档。

DoD：
- 公测期无 P0 级可靠性 issue 挂起 ≥ 1 周；
- 升级路径经真实测试；
- v1.0 发布说明与迁移文档齐备。
