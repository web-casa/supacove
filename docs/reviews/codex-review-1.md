# 9-Phase 开发方案评审

评审对象：`docs/dev-plan.md` 当前版本；评审日期：2026-10-03。共 **30 项：P0 8 项、P1 18 项、P2 4 项**。

这是方案评审，不是实现审计；当前仓库可见材料只有开发方案，没有可执行实现供验证。下文把已经存在的矛盾与尚未定义的关键协议分别说明，不把遗漏推断成已经发生的漏洞。事实核对使用 PostgreSQL、平台、存储和库的官方资料；排期估计属于工程判断。

方向成立：Go 单体、SQLite 持久任务、官方逻辑导出、用户自带对象存储，以及可脱离应用恢复的交付方式，适合单人维护。真正的风险集中在“成功”“验证”“保留”的定义及其崩溃边界。无 Docker socket 的临时 PostgreSQL 在技术上可做，但不能因此推导出安全隔离，也不能因此承诺恢复到任意托管平台。

## [P0 必须修改]

### P0-01 恢复密钥没有初始协议，灾难时可能只有密文

**所在 Phase：** P2、P5、P6、P9。

**问题：** P2 定义了凭据 AES-GCM 主密钥，却没有定义 age recipient/identity 的来源、保存和导出。P6 自动解密要求实例可访问恢复私钥；若实例只持公钥就无法自动验证。P9 才安排“丢失恢复私钥”提示，晚于首次产生不可恢复的密文。两类密钥混用还会让丢失应用主密钥同时毁掉凭据和备份恢复能力。

**具体修正建议（加入 P2，删除 P9 才首次处理的安排）：**

> 首次备份前配置 age 恢复公钥，记录 key ID/recipient 指纹；恢复私钥与凭据 AES-GCM 主密钥用途分离。用户须将恢复私钥离线保存，UI 提供备份与试解密流程。启用自动验证时，显式配置供验证使用的 identity secret 挂载，并说明实例可解密的信任边界；未配置时保持 verification=not_configured。私钥、口令及应用主密钥不进入 manifest、恢复包、API 普通响应或日志。v1 支持新备份切换 recipient，旧备份保留原 key ID，不宣称旧密文已重新加密。

**验收：** 删除应用容器和 SQLite，仅使用桶文件、离线私钥及 age/PG 工具恢复成功；错误私钥、丢失主密钥和重建实例不能被自动生成新钥掩盖。AES-GCM 另须规定每次加密唯一 nonce、认证失败处理和密钥文件权限。

### P0-02 流式链路缺少成功提交条件，截断 dump 也可能是合法 age 文件

**所在 Phase：** P2、P3、P6。

**问题：** 流式加密本身可行；但 pg_dump 中途失败后，已经输出的部分内容仍可能被 age 正常封装。SHA-256、age 可解密都不能证明导出完整。方案未规定进程退出、管道复制、加密 Close、磁盘同步各自错误的汇聚；P2“清理暂存”和 P3“暂存密文重传”也缺乏生命周期衔接。age Go API 明确要求关闭 writer 才能写完最后一个块。[age API](https://pkg.go.dev/filippo.io/age)

**具体修正建议（替换 P2 执行链路的提交部分）：**

> 仅在 pg_dump 退出码为 0、所有流复制成功、age writer.Close 成功、文件 Sync/Close 成功后，原子提交本地 artifact_ready；使用临时文件并在提交前重命名及同步所在目录。任一环节失败不得产生成功备份记录。stderr 并发读取、限量保存并脱敏；取消或超时终止进程组，等待子进程退出和管道收敛。密文直到远端提交完成才进入可回收集合，上传重试复用相同 artifact。

**验收：** 注入“先输出数据再非零退出”、Close/Sync 失败、消费者提前失败、取消时子进程存活；均不能进入成功状态，无死锁、泄漏或误删待重传文件。

### P0-03 SQLite 与桶之间没有可恢复的提交协议

**所在 Phase：** P2、P3、P4、P6。

**问题：** “上传完成”“清单落库”“启动将 running 标记 interrupted”不足以解决上传完成后落库前崩溃、远端成功响应丢失、manifest 上传失败、删除成功后落库失败。对账只能发现差异，无法决定是否续传或清理；若启动就删掉所有“孤儿”，会毁掉合法待重试密文。

**具体修正建议（加入 P3，状态模型在 P2 先建立）：**

> attempt 与 backup artifact 分开建模。每个备份有不可变 backup_id、目的地快照、对象键、内容大小/哈希及可用的 version ID。预先落库上传意图；上传并核验密文后，发布版本化 manifest 作为远端提交标记，最后更新本地状态。重启按持久意图与远端对象核对，幂等完成提交或继续上传，不重新 dump。未提交对象隔离并在宽限期后处理；不能仅按文件名或任务 running 状态清理。删除采用 deleting→逐对象删除→确认→deleted，可重复执行。

**验收：** 在每个外部副作用前后强制崩溃，重启后既不重复导出，也不将未提交备份算作可恢复；保留与对账不能删除仍被上传/下载/验证任务引用的对象。

### P0-04 验证门控保留规则存在无界增长和错误替换

**所在 Phase：** P3、P6。

**问题：** “仅通过恢复验证的备份计入保留名额”意味着失败/未验证对象可能永不清理，验证因缺扩展长期失败时会持续涨账单。“无验证时回退”没有区分主动关闭、超阈值跳过、队列积压和验证失败；不能在失败后自动降低保护标准。三模式、配置变更和来源变化时，“最新一份”也没有明确保护域。

**具体修正建议（替换 P3/P6 保留条款）：**

> 保留按数据库稳定 ID、目的地及可恢复配置域计算。完整、结构、数据备份分别展示，部分备份不能替代完整备份的保护锚点。删除候选包含超期的已验证/未验证/失败对象，但排除保护锚点和活动引用；未验证/失败对象使用显式宽限期与数量/字节预算。新锚点须远端提交、完整性通过且满足该域配置的验证等级后，事务替换旧锚点。验证失败/积压不触发降级；只有用户明确不启用验证的域采用完整性锚点。预算与保护冲突时停止自动删除并告警，不突破保护规则。无锚点时禁止破坏性自动清理。

**验收：** 验证连续失败 30 次、保留数 1、按天到期、最新对象人为丢失、切换密钥/模式/排除规则、删除与验证并发时，保护不被突破；失败对象的增长受到明确策略控制。将“至少保留一份”表述为工具删除保证，不能保证用户桶生命周期或人工操作不删。

### P0-05 同容器临时 PostgreSQL 缺少安全信任边界

**所在 Phase：** P6；需在 P1/P2 做可行性验证。

**问题：** non-root、随机端口和无 Docker socket 都不是隔离机制。恢复会执行源端超级用户选择的代码；若临时 PG 与应用同 UID、可读主密钥/PGPASSFILE/SQLite，恶意 dump 或函数可能触达全部凭据。临时 PG 使用超级用户恢复时尤其危险。官方也明确警告恢复非可信 dump 的任意代码风险。[PostgreSQL pg_dump 安全警告](https://www.postgresql.org/docs/current/app-pgdump.html)

**具体修正建议（加入架构 ADR）：**

> v1 自动验证仅支持管理员信任的来源，不承诺不可信 dump 沙箱。验证只监听独占目录下的 Unix socket，禁用 TCP 监听；独占实例、受控环境变量、禁止加载任意用户指定扩展。P1/P2 验证单容器非 root 下文件/进程隔离是否实际可实现；若验证进程仍能读取应用 secrets，发布文档与 UI 明确该边界，并要求显式启用。需要不可信来源隔离时采用无共享 secrets/数据卷的独立受限验证进程环境或外部验证器，不能用 nice 代替隔离。CI 验证容器不注入平台/桶真实凭据。

**验收：** 用含文件读取及程序执行尝试的测试 dump 检查可见目录和权限；输出隔离测试证据或受信任来源限制。不要为了隔离临时添加 root/特权并破坏已锁定部署前提。

### P0-06 裸 PG 验证环境不能代表托管平台可恢复性

**所在 Phase：** P2、P5、P6。

**问题：** 内置服务端主版本未指定。真实 dump 依赖扩展及版本、角色、owner/ACL、locale、预加载配置和平台 schema；只有 PG 二进制的 initdb 环境经常恢复失败。反过来用 --no-owner/--no-acl 跳过角色错误后成功，也不能声称原始权限恢复成功。数据-only 无 schema 无法独立恢复到空库；结构-only 不应做数据比对。P6 的“恢复已验证”目前过度承诺。

**具体修正建议（替换 P6 验证目标与状态）：**

> P2 收集所需扩展/版本、角色引用、编码/locale、dump/restore 版本与模式。P6 为已测试的 PG 与扩展组合维护验证 profile，固定目标版本、角色初始化及恢复选项；不支持的依赖标记 unsupported，资源超限标记 skipped，SQL/解密失败标记 failed，三者均不算通过。通过状态显示“在 profile X 上按选项 Y 恢复成功”，并区分数据恢复验证与权限/平台完整恢复演练。仅数据备份须有绑定的 schema 基线及恢复依赖，否则不提供独立恢复验证；仅结构备份只验证结构。

**验收：** 无扩展、pgvector 等已支持扩展、缺失扩展、缺 owner、RLS、自定义角色及三备份模式分别得到确定结果；不能靠忽略 SQL 错误变绿。与 P0-07 配合，平台演练单独记录。

### P0-07 Supabase 不能仅靠普通 -Fc 加一份指南变成可靠恢复

**所在 Phase：** P2、P5、P6。

**问题：** Supabase 新项目已有平台 schema/角色，普通全量 pg_dump 恢复会遭遇对象冲突和权限问题。官方流程是分开导出角色、结构、数据并处理托管对象和触发器；官方也明确提示原始 pg_dump 包含内部对象会带来恢复权限错误。当前方案没有定义 Auth/Storage 元数据、用户自建托管 schema 对象、Vault 等的具体策略。裸 PG 验证通过并不意味着恢复到新 Supabase 项目成功。[官方迁移流程](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)、[官方自部署恢复说明](https://supabase.com/docs/guides/self-hosting/restore-from-platform)

**具体修正建议（将 P5 恢复 profile 的技术 spike 提前到 P2）：**

> 保持 pg_dump -Fc 的既定主格式，先实现并实测 Supabase 专用导出/恢复 profile，明确平台 schema 的结构/数据选择、已有对象处理、角色映射、触发器/RLS、扩展及外部密钥前置条件；必要时以多个官方工具产物组成一个逻辑备份集合。若 beta 仅支持应用 schema，明确写“应用 schema 逻辑备份”，不得暗示包含全部 Auth/Storage 元数据。禁止把 CLI SQL 模板直接套到 -Fc；禁止把所有恢复错误当作可忽略的平台噪声。缺失能力显示为不支持的恢复目标。

**验收：** 新建真实 Supabase 目标，验证业务表、Auth 用户、跨 schema FK、自定义角色/RLS、Storage 元数据及声明支持的 Vault 场景；未支持的内容列为排除项。若该 profile 的实施必须改变锁定产物格式，先提交具体 ADR 由负责人决策，不能悄悄改格式。

### P0-08 自身状态与升级恢复被推迟到 beta 之后

**所在 Phase：** P1、P3、P5、P9。

**问题：** P9 才做迁移和自身数据备份指导，但 beta 已承载用户凭据、调度、密钥引用和保留锚点。SQLite 丢失后仅“列桶对账”无法重建来源/密钥/恢复选项，重建实例还可能误清理旧对象。WAL 中活跃数据不能简单只复制 `.db` 文件。[SQLite 在线备份 API](https://www.sqlite.org/backup.html)

**具体修正建议（移到 beta 门禁）：**

> P1 定义状态目录和 secret 挂载，P3 发布远端自描述 manifest/恢复资料，P5 完成脱离实例的恢复演练。P8 前提供一致的 SQLite 备份/停机备份流程、主密钥独立保管说明，以及上一公开版本→新版本的前向迁移测试；迁移前自动生成一致备份，失败拒绝提供写服务。无法逆向迁移时明确回滚需要恢复迁移前状态。丢失 SQLite 后只读发现旧备份；未确认归属和保护锚点前禁用旧前缀清理。

**验收：** 从上一 beta 数据卷升级，模拟迁移失败并恢复；在 SQLite/WAL 丢失、应用主密钥丢失、仅桶和恢复私钥幸存三个场景给出确定行为。manifest 至少含 backup ID、格式版本、对象引用/大小/哈希、时间语义、模式/选择规则、工具版本、key ID、依赖和恢复 profile；不得含密码或私钥。

## [P1 强烈建议]

### P1-01 客户端 ≥ 源版本不是完整的兼容策略，PG13 已停止维护

**所在 Phase：** 锁定决策、P2、P6、P8。

**问题：** 新客户端可导出受支持的较旧服务器，但选 PG18 导出 PG13 并不保证再恢复回 PG13；目标主版本、归档格式和 pg_restore 能力都要参与检查。按评审日期 PG13 已于 2025-11-13 EOL，PG14 将于 2026-11-12 EOL。六套客户端加不明版本服务端扩大镜像维护负担。[pg_dump 兼容说明](https://www.postgresql.org/docs/18/app-pgdump.html)、[版本支持政策](https://www.postgresql.org/support/versioning/)

**具体修正建议：**

> 优先选源库同主版本客户端；没有匹配版本时，只使用通过实际恢复矩阵的较新客户端，记录其目标版本限制。manifest 写源/dump/restore/验证目标版本及压缩算法。每次 beta 发布重新核对支持窗口；PG13 源连接可作为遗留兼容项，但不默认捆绑已 EOL 二进制或宣称受支持。镜像多版本方案在 P1 做双架构原型并制定补丁更新策略。

**验收：** 同版本、允许向上恢复、明确拒绝向下恢复、旧 pg_restore 读新 archive 的失败均有用例。无需做六乘六全组合，但必须说明测试过的边和拒绝的边。

### P1-02 TLS 与连接参数必须统一，PGPASSFILE 不能解决所有泄露

**所在 Phase：** P2、P4、P5。

**问题：** pgx 连接测试与 libpq/pg_dump 配置可能不同；“TLS 检查”没有规定是否验证证书和主机名。sslmode=require 不能一概当作身份验证。若完整带密码 URI 仍传到 argv，创建 PGPASSFILE 没有意义；URI 还可能指定本地文件路径或特殊 libpq 参数。[libpq TLS 语义](https://www.postgresql.org/docs/current/libpq-ssl.html)

**具体修正建议：**

> 将连接串解析为受支持字段，pgx 与 libpq 使用统一的 host/user/db/TLS/CA 语义；远程连接默认推荐 verify-full，未验证证书及明文连接需要明确配置并持续显示状态。子进程 argv 不含密码，PGPASSFILE 权限 0600、目录 0700，正确转义冒号/反斜杠，清理所有分支。限制用户传入的 passfile/service/sslkey/options 等路径或自由参数；不开放任意 pg_dump flags。启动子进程时清理继承的 PG* 和无关 secret 环境变量。

**验收：** 错主机名/错误 CA/过期证书、特殊字符口令、pgx 成功但 dump 失败、`/proc` argv 与四类输出脱敏都有断言。

### P1-03 行数估算和数据库大小不能作为恢复一致性的判据

**所在 Phase：** P2、P6、P8。

**问题：** 统计行数会过期；恢复后未 ANALYZE 的估算可能无效。库体积受膨胀、索引构建及版本影响，不应要求相等。源端另一次查询的行数可能与 pg_dump 一致快照不同。普通表数量相同也不能检测漏行、错值或缺索引。

**具体修正建议：**

> 最低验证判据是远端完整读取/解密成功、pg_restore 零错误以及预期 TOC/对象集合恢复；估算行数和库体积只作诊断。确需源/恢复精确行数对比时，用显式导出的同一 snapshot 供 pg_dump --snapshot 和计数查询使用，并标明额外负载及 sequence 等非 MVCC 状态限制。生产默认不做逐表全量 COUNT；CI 用静态 fixture 的已知精确数据、关键对象与内容断言。

**验收：** 并发写入、过期统计、空表、分区、索引重建不会产生错误成功或不必要失败。快照能力见 [pg_dump --snapshot](https://www.postgresql.org/docs/18/app-pgdump.html)。

### P1-04 nice 和压缩体积阈值不能治理恢复资源

**所在 Phase：** P2、P6、P8。

**问题：** nice 只影响 CPU 调度优先级，不限制 CPU 时间、内存、磁盘或 I/O。小密文可能恢复出很大的表和索引。异步验证若不限队列及并发，会与导出争用磁盘并让调度超期。

**具体修正建议：**

> 导出与验证使用统一资源准入；验证并发固定 1、有界队列，积压时合并尚未开始的旧验证或显式 skipped。按解压后的估计数据/索引及 WAL 峰值预留磁盘，运行中持续检查独立工作目录预算；设置明确 wall-time、进程/FD/内存策略并验证容器配额行为。备份优先，验证不满足预算时延后，不能挤掉待上传密文。退出与启动均回收残留 PG 进程/socket/目录。

**验收：** 高压缩比、验证 OOM、WAL/索引写满、超时和 restart 时主备份链仍按明确策略工作。区分应用逻辑配额、文件系统硬配额和容器整体限额，不把检查 free space 称作硬隔离。

### P1-05 持久调度缺少原子去重、积压和配置变更语义

**所在 Phase：** P2、P4。

**问题：** 没有唯一键和事务边界，时钟回拨/重启后可重复入队。全局并发 1 下，上传长时间重试或一次大库会饿死其他库；catch-up latest 并不自动处理已堆积 pending。暂停、改 cron、删除来源/目的地时任务使用什么配置未定义。

**具体修正建议：**

> 调度入队与 next_due 更新在一笔 SQLite 事务内，唯一键使用 database_id/schedule_revision/scheduled_at_utc；重试关联原任务，手动任务有独立幂等键。pending 有界，同库合并过期未开始计划，公平轮转；上传重试等待释放执行槽。任务保存配置快照/版本，删除或修改配置时显式处理 pending 和活动引用。cron 存 IANA 时区，定义 DST 重复/缺失时间；任务时限用单调时间，计划时刻用 UTC。

**验收：** 在入队事务前后崩溃、跳过多个周期、时钟前后跳、DST、暂停/修改计划、长上传重试及立即备份并发时验证唯一性和有界队列；不承诺网络副作用 exactly-once。

### P1-06 认证和错误分类依赖排得过晚

**所在 Phase：** P1、P2、P4、P8。

**问题：** P2 已存生产秘密、P3 可签下载链接，P4 才加入认证；错误分类到 P8 才完整出现，但 P2–P4 已需要按可重试性决策。“未认证 API/UI 全部 401”排除了登录、初始化、健康检查等必要例外，也无法描述 SPA 页面正常跳转。

**具体修正建议：**

> P1 完成单管理员 bootstrap 和默认访问限制，P2 前启用认证/CSRF；P4 补 UI 与子路径。首次初始化使用一次性 secret 或本地 CLI，不能由公网首个访问者抢占管理员。密码用适合密码的 KDF，登录限流；密码重置撤销全部 session。仅显式列出的登录/静态资源/最小 liveness 匿名，敏感 API 401、登录页面可访问；metrics 和详情健康检查默认受保护。P2 定义 error_class/retryable/code，P8 只补文案和覆盖。

**验收：** bootstrap 抢占、跨站请求、session fixation/撤销、反代 HTTPS Cookie/可信代理与子路径都有集成测试。私有内部原型可以保留，但 DoD 须写清网络暴露限制。

### P1-07 HTTP 外连及生成文本有 SSRF/注入边界

**所在 Phase：** P3、P5、P7。

**问题：** 自定义存储 endpoint、Webhook、死人开关 URL 都让服务端发起网络请求。Token 若跟随任意重定向可能泄露。备份工具需要合法访问内网 PG/MinIO，因此简单封禁所有私网会损害自部署。shell 参数直接拼接来源名称/连接串也会产生恢复脚本注入。

**具体修正建议：**

> 平台 API 固定官方 origin，不接受用户指定 base URL，不向跨 origin 重定向转发 Authorization。HTTP 出站只允许规定 scheme，设连接/读取超时与响应体上限；默认拒绝 metadata/link-local 地址，内部 endpoint 通过管理员显式配置允许，解析与重定向均复核。对恢复脚本采用固定模板与安全参数输入，不把用户字段拼成可执行 shell。下载 URL 作为 bearer secret 脱敏，短期签发；不通过任意 URL 代理下载。

**验收：** 重定向、DNS 地址变化、metadata URL、带换行/反引号/命令替换字符的字段不会泄露凭据或执行代码。此处要求政策可配置，不是假设多租户产品。

### P1-08 分片和对象版本遗漏会持续收费，删除 200 也未必全部成功

**所在 Phase：** P3、P8。

**问题：** 重启可能遗留 multipart parts；仅 DeleteObject 不保证真正回收版本对象，B2 尤其需要 versionId。批量删除还需检查每个对象结果。Object Lock/生命周期、分页、未完成上传也影响对账和“总量上限”。[B2 Delete Object 语义](https://www.backblaze.com/apidocs/s3-delete-object)

**具体修正建议：**

> 明确重试采用完整重传还是续传；v1 可完整重传，但须持久记录并尽力 abort multipart、提供遗留分片回收/桶规则指导。记录上传返回的 version ID，删除处理批量响应内逐对象错误；对保留版本/锁定对象报告未回收字节。列表与对账覆盖分页，始终限制工具 namespace。工具不修改已有桶生命周期；向用户提示外部规则可删除保护锚点。总量上限仅能约束本工具可观测/可删除的范围。

**验收：** 进程死于 multipart、>1000 对象分页、B2 历史版本、部分 DeleteObjects 失败、锁定对象拒删和权限不足。

### P1-09 “远端回读或等价机制”必须成为逐家可验证的协议

**所在 Phase：** P3、P5、P6。

**问题：** 方案没有定义 SHA-256 是密文还是 dump，HEAD 大小、用户 metadata 和 ETag 都不等价于完整内容校验；分片 checksum 也可能是 composite。AWS SDK 默认校验行为会随模块版本变动，S3 兼容存储并不支持相同能力。新 transfermanager 确实存在，不能称作虚构接口；但当前官方模块仍为 v0.x，应钉版本并实测。[AWS 校验文档](https://docs.aws.amazon.com/sdk-for-go/v2/developer-guide/s3-checksums.html)、[transfermanager API](https://pkg.go.dev/github.com/aws/aws-sdk-go-v2/feature/s3/transfermanager)、[R2 兼容表](https://developers.cloudflare.com/r2/api/s3/api/)

**具体修正建议：**

> 默认 manifest 的 SHA-256 指完整密文。每个 provider adapter 明确小对象/分片上传的 checksum 支持、SDK 配置和远端验证算法；不支持与本地完整哈希等价校验时，完整流式 GET 后计算 SHA-256。验证必须读到 EOF 并核对字节数；若 P6 读取远端密文，可合并完整性校验，避免再下载一次。恢复说明包同时说明哈希只检错、不构成独立来源认证，age 也不是发送者签名。

**验收：** 错误 checksum、metadata 正确但内容错误、相同大小替换、分片、下载中断、缺 checksum 响应均有真实 provider 用例。不要把 S3 的一种配置笼统用于 R2/B2。

### P1-10 覆盖声明没有落到实际对象与依赖

**所在 Phase：** P2、P4、P5。

**问题：** “完整”容易被理解为 cluster 或平台完整备份；pg_dump 单库不含全局角色定义。`-n` 是包含 schema，`-N` 才是排除；选择 schema 不自动闭合跨 schema 依赖，还可能遗漏 large objects。FDW 远端数据不是默认覆盖。权限预检也不能静态证明全部导出一定成功。[pg_dump 范围与选择规则](https://www.postgresql.org/docs/current/app-pgdump.html)

**具体修正建议：**

> 产品用语统一为“所选范围的结构+数据逻辑备份”。manifest 固化选择/排除规则并记录实际归档 TOC 对象集合；逐项声明角色/表空间、外部表数据、large objects、扩展依赖与平台外部资源覆盖情况。修正文字为“schema 包含 -n / 排除 -N”。部分 schema 跨依赖预检，缺依赖列入恢复前置条件；禁止为绕过 RLS 错误静默启用 --enable-row-security，失败应明确报告覆盖不足。

**验收：** 跨 schema FK/类型/函数、分区、large objects、FDW、RLS 无 bypass 权限和权限运行中变化；导出成功记录不掩盖 stderr 警告，规则变化形成不同恢复配置域。

### P1-11 恢复包“自包含”与流式恢复的边界不清

**所在 Phase：** P2、P5、P6。

**问题：** restore.sh 仍依赖 age、pg_restore/psql 及相容版本，应称“脱离应用运行”而非没有外部依赖。管道解密后恢复无法直接启用 pg_restore -j；并行恢复要求普通文件/目录。pg_restore 默认遇 SQL 错误继续，需要明确错误处理。[pg_restore 文档](https://www.postgresql.org/docs/current/app-pgrestore.html)

**具体修正建议：**

> 恢复包含非敏感 manifest、校验、固定脚本和平台指南；脚本检测工具/版本，先核对密文完整哈希，检查新建空目标与 profile 依赖，用受限 PGPASSFILE 读密码，默认不使用 --clean/--create。串行流恢复启用 --exit-on-error 并检查 age 与 pg_restore 两端退出；需要并行时先安全解密到 0600 临时文件，要求足够磁盘，trap 清理并提示磁盘上存在明文的边界。失败返回非零并说明目标可能已部分写入，不报恢复完成。

**验收：** 在无本工具的全新主机测试；错密码/私钥、缺工具、旧 restore、非空目标、解密失败和 SQL 错误都有可行动结果。明确 Linux/macOS 支持范围及 shell 要求，不靠 set -e 推断管道安全。

### P1-12 通知需要持久交付，死人开关必须绑定真实备份新鲜度

**所在 Phase：** P3、P4、P7。

**问题：** 若仅在内存里发送通知，状态已提交后进程崩溃就会漏发。上传旧密文重试成功也可能让“每成功后 ping”掩盖数据已很旧。健康检查成功不能替代备份成功。Healthchecks 的周期和 grace 要覆盖排队/执行耗时，否则大量误报。[Healthchecks 协议](https://healthchecks.io/docs/http_api/)

**具体修正建议：**

> 状态提交与通知 outbox 同事务，异步发送、有界重试/退避、event ID 去重；提供发送失败状态与测试按钮，通知失败不回滚备份。每库分别配置外部周期/grace，明确成功等级（至少远端提交+完整性通过），同时校验 snapshot_age 未超阈值，不能用旧 dump 的晚上传成功消除超期。start/fail 与 success 按协议区分；健康检查不发备份成功 ping。通知 URL 当作秘密保护。

**验收：** 在提交后发送前 crash、Webhook 429/超时/重复、旧密文晚上传、长验证和关机场景下告警语义正确。最小失败/超期通知提前到 P4，P7 完善事件覆盖。

### P1-13 缺少 RPO、排队预算和支持容量边界

**所在 Phase：** P4、P7、P8。

**问题：** ≥3 数据库不重叠、≥5GB 测试均不能说明工具可以按时保护用户。单 worker 的稳定条件取决于所有任务总耗时与调度周期；5GB 索引占多的库与 5GB 不可压缩数据的库完全不同。新鲜度应依据导出快照时刻，不是任务结束或上传完成时刻。

**具体修正建议：**

> 每库配置最大可接受备份年龄；记录计划、实际开始、快照/导出起始、上传提交、验证完成各时刻。首页按最近远端可用备份的数据时间计算年龄，验证新鲜度另列。说明本产品 RPO 受计划间隔、排队、执行和故障影响；不承诺 PITR。P8 固定测试机 CPU/RAM/磁盘/网络条件，使用至少一个低压缩数据 fixture，报告 dump/upload/verify 各段耗时、峰值 RSS/磁盘；给出支持的总负载边界。

**验收：** 一个超长任务、三个竞争数据库、断网跨多个周期、验证超阈值跳过时，超期状态均正确；能力不足在配置或运行时可见，而非静默不断积压。

### P1-14 故障测试没有覆盖真正危险的副作用边界

**所在 Phase：** P2–P8、跨 Phase 测试。

**问题：** 当前矩阵偏重“进程中断”，缺少成功副作用后的 crash、源端并发变化、控制状态磁盘写满、密钥错误和删除竞态。截断 age 文件只能证明检测加密层损坏，不能证明 SQL 恢复/数据质量验证有效。Testcontainers 日常测试需要 CI Docker 能力，与发布镜像无 socket 要分开。

**具体修正建议（补充跨 Phase 门禁）：**

> 建立可定位步骤的故障注入点：dump 退出/age Close/文件 Sync、multipart 完成、manifest 发布、SQLite 提交、通知 outbox、删除前后。使用真实 PG fixture 覆盖 bytea/大字段、sequence、分区、FK、索引、视图、RLS、角色和已支持扩展；静态数据精确核对。恢复损坏测试分为传输截断、合法 age 封装的无效 dump、缺角色/扩展 SQL 错误、声明对象缺失。测试 SQLite 与暂存分别 ENOSPC、SQLITE_BUSY、超时、OOM/kill 及取消。DoD 保留 fixture ID、seed、工具/profile 版本与结果。

**验收：** 可重复执行的 Go 集成测试与发布演练记录，而非一句“手测通过”。单测用 fake clock 测调度，真实存储测 SDK 能力，Playwright 测 UI 状态；`-race` 只检测 Go 内存竞态，不能替代 DB/进程/对象一致性测试。特权故障注入放 CI 测试夹具，另做发布容器非 root/无 socket 黑盒测试。

### P1-15 DoD 内部冲突，“或者验证通过”放宽了平台恢复门禁

**所在 Phase：** P2、P3、P4、P5、P6、P8、P9。

**问题：** P5/P8 要真实平台恢复，跨 Phase 却允许“恢复（或验证通过）”，裸 PG 验证可绕过目标平台问题。P9“无 P0 挂起 ≥1 周”允许刚报告的 P0 带病发布。P2“日志搜不到连接串”不能证明未知 secret 没泄漏；“任何故障都不删”是无限量化，不可验证。

**具体修正建议（统一 DoD）：**

> beta/v1 发布候选必须完成三个已声明支持平台的真实备份→从桶下载→依恢复包在新目标手动恢复，自动验证是额外门禁，不作为替代；提交脱敏演练记录、artifact ID、profile/工具版本及 fixture 断言。v1 发布时所有已知 P0 为 0、恢复相关 P1 已关闭或明确缩减支持范围，稳定观察窗口内无未解释的成功假象/误删。日志/错误/Webhook/脚本/API 使用植入 secret canary 与变体扫描；故障保证限定为已列举并自动化的矩阵及明确不变量。

**验收：** CI 可以判定每个门禁通过/失败；新增未测试平台或未解决 P0 自动阻止发布。不能把“首次备份成功”当作“可恢复”验收。

### P1-16 14 周没有风险余量，P5/P6 是主要超载点

**所在 Phase：** 总体节奏、P1–P9。

**问题：** P1–P8 标注时间相加恰好 14 周，并非带区间和缓冲的估计。P5 2.5 周同时交付三 API 导入、权限/网络诊断、平台恢复语义、脚本和 UI，P6 2 周承担服务端打包、扩展/安全/资源治理/保留重构，明显乐观；P3 的三真实 provider 分片与一致性在 2 周内也偏紧。P8 才暴露恢复或安全问题会返工内核。

**具体修正建议（直接替换里程碑与依赖文字）：**

> M2 改称“beta 功能候选，限已测试 profile”，不称“功能完整的 v1”。P1/P2 提前 spike Supabase -Fc 恢复与嵌入式验证/双架构打包，并先实现认证、密钥协议、状态和错误分类。P3 保留先采用完整性锚点，P6 只增加显式验证等级。P4 做最小失败/超期告警，P5 做向导与恢复包体验，P8 集成验收而非首次安全/容量验证。P9 仅稳定化及 v1 门禁，第二层能力另设后续迭代。

**可执行排期建议（工程估计）：**

| Phase | 完整声明范围的建议工期 | 14 周 beta 的削减措施 |
|---|---:|---|
| P1 | 1–1.5 周 | 保留骨架/访问限制；增加关键 spike |
| P2 | 2–3 周 | 保留内核、密钥、manifest 和崩溃协议 |
| P3 | 2–3 周 | 共用 S3 adapter；先简单按份/按天，无总账单上限 |
| P4 | 1.5–2 周 | 保留可靠调度；子路径可推迟并明确不支持 |
| P5 | 3–4 周 | 三平台连接串向导和恢复 profile 保留；Token 自动导入推迟 |
| P6 | 3–4 周 | 限定 PG/扩展 profile；可信来源显式启用，不做全组合 |
| P7 | 1–1.5 周 | Webhook+每库死人开关，少量指标 |
| P8 | 2–3 周 | 安全/恢复/容量门禁保留；推广物料减少 |

完整范围合计 **16–22 周，另留 2–3 周风险缓冲**；该范围不是交付保证。坚持 14 周时，必须在开工前落实右列缩减，并给出两周左右集成余量；不能同时承诺原完整范围与确定日期。三备份模式中的仅数据/仅结构可在 beta 后加入，省下依赖配对、验证和保留复杂度；这是范围调整建议，需产品负责人定版。

### P1-17 SQLite 配置与锁文件的实际保证不足

**所在 Phase：** P1、P2、P4。

**问题：** WAL 仍只有一个 writer；`foreign_keys`、busy timeout 等连接级参数可能只作用于连接池某条连接。WAL+NORMAL 不保证断电后最近事务仍在。仅检测锁文件存在会留下 stale lock，不能保证第二实例排他；WAL 不适合跨主机共享网络文件系统。[SQLite WAL 限制](https://www.sqlite.org/wal.html)、[synchronous 语义](https://www3.sqlite.org/pragma.html)

**具体修正建议：**

> 显式定义所有连接的 PRAGMA 初始化、短写事务、busy timeout/重试和持久性策略，关键状态采用适当同步等级并做吞吐测试。调度/保留/迁移不要在 SQLite 事务内等待外网。使用 OS advisory lock，在持锁后迁移和启动，进程死亡自动释放；仅支持单实例本地持久卷，明确排除 NFS/RWX 多主机部署。主进程锁不替代验证子进程的退出回收。

**验收：** 多 writer 争用、SQLite 写满、两个容器同时启动、kill 后重启、迁移锁与心跳更新；用实际连接池验证 PRAGMA，而非只检查启动日志。

### P1-18 三平台发现 API 与连通性不能靠名称/端口推断

**所在 Phase：** P1、P2、P5。

**问题：** Supabase API Token 能发现项目不等于能拿到现有数据库密码；方案未保证提示用户补齐凭据。仅见 6543 或 5432 无法通用判断池化模式，Supabase 直连存在 IPv6 限制。Neon 导出需直接连接并考虑 compute 唤醒；Railway 若应用部署在同私网，私网地址可能完全合法，不能一律强制公网代理。[Supabase 连接方式](https://supabase.com/docs/guides/database/connecting-to-postgres)、[Token 与数据库密码区别](https://supabase.com/docs/guides/platform/personal-access-tokens)、[Neon 官方导出指南源码](https://github.com/neondatabase/website/blob/main/content/docs/guides/export-neon-postgres-compatible.md)、[Railway TCP/私网](https://docs.railway.com/networking/tcp-proxy)

**具体修正建议：**

> 先用真实只读 Token 记录每平台 API 能返回的字段、权限范围、分页/429/撤销行为和缺失字段；缺密码明确要求用户输入或粘贴完整连接串，不重置密码。池化识别使用官方 endpoint 特征与连接行为，端口仅为提示，保留用户确认和通用连接兜底。Supabase IPv4-only 时引导官方 session pooler，不由项目 ref/region 臆造 pooler host。Railway 从部署位置检查可达性，仅私网不可达时引导配置 TCP proxy。Neon 唤醒设置独立连接超时，区分暂时启动与认证失败。

**验收：** 受限/撤销 Token、缺字段、分页/限流、IPv4-only、代理端口自定义及同私网成功路径；mock fixture 从真实 API 脱敏样本生成，不能自行发明返回结构。

## [P2 可考虑]

### P2-01 统计命名与指标基数需收敛

**所在 Phase：** P4、P7、P8。

**问题：** -Fc 默认已压缩，“dump 大小/压缩后大小”可能重复；密文体积并不是再次压缩结果。成功率若把验证/通知失败混进任务失败，用户会误读。每表/backup ID/错误字符串作为 Prometheus label 会无界增长。

**具体修正建议：**

> 只记录源库物理体积、已压缩 archive 字节数、age 密文字节数，各标注测量口径；无测量值显示未知，不估成精确数。分开统计导出、远端提交、恢复验证、通知结果；metrics 不使用 task/backup/table ID 或自由错误文本 label，历史明细放 SQLite。

**验收：** 一个任务验证失败但远端备份有效时两种状态不混淆；持续执行后时间序列数量有明确上限。

### P2-02 v1 API 冻结不应扩大到内部 UI 契约

**所在 Phase：** P1、P9。

**问题：** OpenAPI 契约先行有价值，但单人产品过早承诺所有 API 永久稳定，会束缚状态机改进；“AI 解释位留接口”在无实现和用户需求时也增加维护表面。

**具体修正建议：**

> v1 明确稳定承诺范围：manifest/recovery kit 格式的版本兼容、CLI 恢复入口及公开自动化 API；内部 UI API 可随版本演进。没有真实需求的 AI 接口不进入公开契约，仅内部模块边界预留。变更先更新 OpenAPI，并验证生成客户端行为与运行时校验。

**验收：** 文档列出哪些接口受语义化版本约束；旧 manifest 能由新版恢复脚本识别，未知版本明确失败。

### P2-03 竞品“护城河”和许可证描述需要更准确

**所在 Phase：** 锁定决策、P1、P9、跨 Phase 阅读计划。

**问题：** 在纯开源定位下，“护城河不上交”只能表示不主动向上游提交，不能表示别人无法合法复用。AGPL 也不能禁止符合许可证的云端再包装。stars、行数、目录和竞品能力是动态信息，不宜成为架构定论；竞品现已公开提供恢复验证能力，差异化要落到无 socket 部署约束及平台恢复质量。[Databasus 官方恢复验证](https://databasus.com/restore-verification/)

**具体修正建议：**

> 将竞品策略改为“独立实现，通用修复可按维护成本回馈；平台体验由本项目优先投入，不保证排他性”。许可证 ADR 写明社区贡献/托管使用目标，避免承诺 AGPL 能阻止合规托管；再发行与借用按实际依赖许可证保留必要声明。引用竞品设计记录固定 commit 和文件路径，借用代码保留来源/许可证/改动说明。

**验收：** 删除未核实的规模数字作为决策依据；README 用可测试差异而非 stars 排名解释产品价值。许可证定版本身仍需负责人选择，本评审不替其作法律结论。

### P2-04 健康检查和诊断可以减少对生产库与桶的扰动

**所在 Phase：** P3、P4、P7。

**问题：** 定期完全复用写入→读回→删除向导测试会制造请求费用和删除失败垃圾，也可能唤醒 Neon compute。应用存活、调度器存活与“用户数据受保护”应分别表达。

**具体修正建议：**

> /healthz 只回答进程存活，readiness 回答本地状态/调度能力；备份新鲜度在授权状态接口与外部死人开关呈现。周期连通性探测低频、有 jitter、有超时，默认优先使用最近实际备份结果；完整存储写读删探测用于初始化和用户主动诊断，若周期启用须说明成本与临时对象回收。

**验收：** 健康检查不会把桶短暂不可达映射为应用不断重启；诊断对象与正式备份使用不同 namespace，不干扰保留/对账。

## 总体结论

**修改后通过。** 核心技术路线可行，无需重做架构；但当前版本不足以支撑“功能完整 v1、14 周确定 beta”的承诺。P0 应先进入方案和状态/产物协议，再实施，而不是留待发布安全审计。P1 中的恢复、调度、故障测试和升级门禁应在 beta 前落实；若无法落实，公开缩减支持范围。

最关键的 3 件事：

1. **先定义可恢复备份的提交与保护协议。** 把密钥、完整导出、远端 manifest、崩溃恢复、保留锚点及离线恢复作为一条闭环，明确每个成功条件。
2. **提前证明两个最难的差异化承诺。** 用真实 Supabase 新目标证明恢复 profile，用发布形态容器证明嵌入式验证的依赖、资源和信任边界；不要等 P5/P6 才发现路线受限。
3. **让时间服从范围与证据。** 14 周 beta 推迟 Token 导入、部分备份模式和第二层能力，保留真实恢复、故障注入与升级门禁；完整原范围按 16–22 周加缓冲规划。
